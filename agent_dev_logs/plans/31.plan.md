# Strategy — Issue #31: Page splitting for generic JSON OCR inputs

> Issue [#31](https://github.com/ufal/atrium-alto-postprocess/issues/31) · Labels: `development`,
> `integration` · Milestone: **Q3 [WP8 / WP7: Advanced Transnational Access & Curriculum Drafting]** ·
> **Status: 🟡 PLANNED — design only, no production code touched yet**

## Context

Issue #31 asks the pipeline to digest any text-containing OCR-engine output — ALTO XML or generic
JSON — into ordered plain text. The ALTO half of that is done: `page_split.py` already splits a
document-level `<file>.alto.xml` (multiple `<Page>` elements under one `<Layout>`) into one
`<base>-<page>.alto.xml` per page (`page_split.py:39-87`), and everything downstream
(`alto_stats_create.py`, the `extract_*_2_TXT.py` family) is built on the assumption that it is
handed one page per file.

The JSON half of the pipeline was built on the **same one-file-one-page assumption**, but nothing
actually enforces or splits toward it — it's just hardcoded:

- `run_pipeline.py`: `INPUT_FORMATS["json"]["split_script"] = None`, with the stage 1 comment
  *"not applicable; each JSON file is already one page"*, and a second comment tagged **`(#31)`**
  explicitly noting the stats-CSV builder has to scan the raw `input_dir` because there is no
  split output to scan.
- `json_stats_create.py`: every JSON file becomes exactly one CSV row with `"page": 1` hardcoded
  (`_process_single_json()`), documented in the module docstring as *"the pipeline's page model for
  JSON is 'one file = one page'"*.
- `extract_JSON_2_TXT.py`: one file in → one `.txt` out, no page concept at all.
- There is no real sample JSON anywhere in `data_samples/` — only synthetic test fixtures
  (`{"page": {"lines": [...]}}`, `{"text": "..."}`). The extractor was deliberately built
  schema-agnostic (`TARGET_KEYS` leaf-walk) rather than against one vendor's format, and **we
  confirmed with K there is no concrete engine/sample to design against yet** — this plan is
  intentionally generic and will be validated against real data whenever a sample shows up.

**Decision (confirmed with K):** unify page splitting into `page_split.py` itself rather than a
parallel script — Step 1 of the pipeline becomes "split whatever page-bearing document you were
given," dispatched by file extension, with the existing ALTO path untouched.

## Research: how OCR/Doc-AI engines represent multi-page documents

Surveyed several real engines; the multi-page shapes fall into three families:

**Family A — nested pages array (most common).** One JSON per document; a top-level (or
one-level-nested) key holds an array of page objects, each appearing in document order with its
own structural fields. Azure Document Intelligence's `analyzeResult.pages` is a list of pages
represented sequentially, each carrying its own orientation angle and dimensions
([Microsoft Learn: Document layout analysis](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0)).
docTR follows the identical shape — blocks/lines/words nested under an indexed `pages` list,
accessed as `output['pages'][0]['blocks']`
([docTR OCR extraction walkthrough](https://medium.com/quantrium-tech/text-extraction-using-doctr-ocr-471e417764d5)).
Google Document AI and most PDF-text-layer dumps (PyMuPDF/pdfplumber-style exports) use the same
`"pages": [...]` nesting.

**Family B — flat element list tagged with a page number.** AWS Textract is the counterexample:
no nesting — a single flat `Blocks` array, where a `PAGE`-type block exists per page and every
other block carries a `Page` field pointing back to it; the total count lives separately in
`DocumentMetadata.Pages`
([AWS Textract: Pages](https://docs.aws.amazon.com/textract/latest/dg/how-it-works-pages.html)).
Splitting this means grouping a flat list by a field value, not slicing a nested array.

**Family C — already one file per page.** This is what the pipeline assumes today, and it's a
reasonable default for this project's domain specifically: pero-ocr — the Brno (DCGM) tool
commonly used on Czech historical/handwritten material — processes images one at a time via its
CLI and emits Page XML/ALTO XML per image, not a bundled multi-page JSON
([pero-ocr GitHub](https://github.com/DCGM/pero-ocr)). Even cloud OCR APIs like OCR.space return
one `ParsedResults` entry per page for multi-page inputs
([OCR.space API docs](https://ocr.space/ocrapi)) rather than one nested blob.

Net: we need to detect Family A and Family B generically and fall back to Family C (today's
behaviour) when neither fires — never assume, never break the current fixtures.

## Detection whitelists (proposed, case-insensitive matching — same style as `TARGET_KEYS`)

```python
# Family A: top-level (or one-level-nested) key whose value is a non-empty list of dicts.
PAGE_LIST_KEYS = {"pages", "page_results", "parsedresults", "page_list", "document_pages", "documentpages"}

# Field checked inside each candidate page-dict / flat-list element (Family A page numbering,
# and Family B grouping key).
PAGE_NUMBER_FIELD_KEYS = {
    "pagenumber",
    "page_number",
    "page_num",
    "page",
    "pageid",
    "page_id",
    "pageno",
    "page_no",
    "physical_img_nr",
}
```

No collision with `extract_JSON_2_TXT.TARGET_KEYS` (text-leaf whitelist) — `"pages"` isn't in that
set, so splitting and text-extraction stay independent concerns operating on the same JSON shape.

## Algorithm sketch for `split_json_document(input_file_path, output_dir) -> int`

1. Load JSON. (No DOCTYPE-style hardening needed — that was ALTO/XML-specific entity-expansion
   protection; standard `json.load` has no equivalent attack surface.)
2. **Family A scan** (depth ≤ 2): find the first key (top-level, or nested one level under a
   dict-valued top-level key) matching `PAGE_LIST_KEYS` whose value is a non-empty list where
   every item is a `dict`. If found and `len(list) >= 1`: that's the page list. Page number per
   item = first matching `PAGE_NUMBER_FIELD_KEYS` field, else 1-based index (mirrors ALTO's
   `PHYSICAL_IMG_NR`-or-index fallback). Each output file = all sibling top-level keys (the JSON
   "header," analogous to `Description`/`Styles`) + that one page object in the container key's
   place.
3. **Family B scan** (only if A found nothing; depth ≤ 2): find any list of dicts where a
   majority of items share a `PAGE_NUMBER_FIELD_KEYS` field, and the field has **>1 distinct
   value** (D6). Group items by value; each output file = full original document with that list
   key replaced by only the matching subset.
4. **Fallback** (D4): neither pattern found → one output file, page number `1`, full document
   unchanged.
5. Write `<output_dir>/<base_name>/<base_name>-<page_number>.json` per page (`json.dump`,
   `ensure_ascii=False`, matching the rest of the repo's JSON I/O style). Return the page count,
   same contract as `split_alto_xml()`.

## File-by-file changes

- **`page_split.py`** — add `split_json_document()` (above); extend `main()`'s file-discovery loop
  to also match `*.json` and dispatch to it; extend the paradata `output_types` to be format-aware
  (`["xml"]` vs `["json"]`) instead of hardcoded. `split_alto_xml()` itself: **no changes**.

  filename-derived `file_id`/`page` (D7); `process_json_files()`/`main()`: scan the split-output

## Risks / open questions

| Risk                                                           | Mitigation                                                                                                                                                                                                                          |
|----------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| No real sample to validate against                             | Ship the generic heuristic now (per K); revisit whitelist thresholds the moment a real engine sample is available. Flagged explicitly in the docstring as provisional.                                                              |
| Family A/B false positives on a genuinely single-page JSON     | D6 threshold (>1 distinct value) for Family B; D5 depth cap for both; Family A additionally requires every list item to be a `dict` (rules out e.g. a `"pages": [1, 2, 3]` page-count field misfiring).                             |
| Two container keys both match `PAGE_LIST_KEYS` in one document | Take the first by depth-then-declaration-order (top-level before nested, first-seen key order); document this precedence explicitly in the docstring since it's the one place behaviour is a judgment call rather than a hard rule. |
| Silent misfire once a real engine is known                     | Worth a config/CLI escape hatch (`--force-single-page` or a config flag) to disable auto-detection per run — **deferred to implementation**, flagging here so it isn't forgotten.                                                   |

## Out of scope (this issue)

- Vendor-specific hardcoded parsers (e.g. a dedicated Textract or Azure adapter) — only revisit if
  a real sample shows the generic heuristic is insufficient.
- Any change to `extract_JSON_2_TXT.py`'s `TARGET_KEYS` text-leaf extraction logic — orthogonal
  concern, already works on split output unchanged.
- The `--force-single-page` escape hatch flagged above — worth doing alongside the main
  implementation, but not blocking it.
